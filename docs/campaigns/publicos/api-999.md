# WhatsApp API e E-mail na jornada; respostas pela caixa; teste no envio direto (#999)

Refs #990. Base: [api-1005.md](api-1005.md) (vínculo campanha ↔ público, regra de consentimento por
linha, `POST /campaign_journey/campaigns` do WhatsApp Oficial). Aceites cobertos aqui: D7, D8, E1
(e-mail e WhatsApp API), J4, L1–L6, N2 (e-mail e WhatsApp API). Este documento é o contrato para o
frontend da jornada.

## 1. O que mudou no comportamento

| Antes | Agora |
|---|---|
| "Respostas vão para a caixa X": `reply_to_inbox_id` só existia no domínio e era ignorado | A campanha tem `reply_to_inbox_id`; o envio por domínio, o envio direto e o teste saem com `Reply-To` = endereço da caixa (§3) |
| "Enviar teste" com envio direto pela caixa respondia `sender_identity_missing` | O teste sai pela caixa, com as mesmas regras (§4) |
| E-mail só com lista importada à parte | Campanha de e-mail criada na jornada recebe os destinatários **do público** (com `contact_id`), mantendo todas as travas (§2.3) |
| WhatsApp API só por etiqueta | Campanha criada na jornada vai para os contatos do público; ficha `{{contact.company}}` (§2.2) |
| Canal desconhecido no endpoint da jornada → `whatsapp_cloud_required` | `unsupported_channel` |

## 2. `POST /api/v1/accounts/:account_id/campaign_journey/campaigns`

Mesmo endpoint, flag (`CAMPAIGN_JOURNEY_ENABLED`, 404 desligada), permissão (`campaign_manage`,
401 sem ela) e envelope de erro do #1005:

```json
{ "error": "<mensagem em inglês>", "code": "<código>", "details": { } }
```

`channel` ∈ `whatsapp_cloud` (api-1005.md), `whatsapp_api`, `email`. Outro valor →
`422 unsupported_channel`. `campaign_import_id` de outra conta → `404`.

Códigos comuns aos três canais:

| `code` | quando |
|---|---|
| `audience_not_ready` | público fora de `completed`/`completed_with_failures`, ou apagado durante a criação |
| `channel_not_in_audience` | **J4**: o canal está desligado no público (`channels.<canal>.enabled != true`) ou a contagem é 0 |
| `invalid_campaign` | validação do model (título vazio, remetente faltando, caixa de respostas inválida…) |
| `channel_not_connected` | o recurso do canal está desligado (`EMAIL_CAMPAIGN_ENABLED`+CRM; `WHATSAPP_API_CAMPAIGNS_ENABLED`) |

O público é travado (`lock!`) e checado de novo dentro da transação, como no #1005: um "Excluir
público" ou "desligar canal" concorrente não passa no meio.

### 2.1 Quem recebe (regra de consentimento por linha)

`CampaignJourney::AudienceContacts` (estendido para e-mail):

- **WhatsApp (Oficial e API):** linha com celular válido na planilha e telefone do contato ainda o
  mesmo (com ou sem o 9). Linha só com e-mail nunca recebe WhatsApp.
- **E-mail:** linha com e-mail válido na planilha (`normalized_email_hash`) e e-mail do contato ainda
  o mesmo (sem diferença de caixa). Linha só com celular nunca recebe e-mail, mesmo que o contato
  tenha e-mail no cadastro. Um destinatário por endereço (a primeira linha vale).
- Quem recusou mensagens ativas (#737) fica fora do total.
- `channels.email.count` e `channels.whatsapp.count` do público são recontados com essa regra ao
  salvar o público; `recipients_count` das respostas segue a mesma regra.
- Falha fechada: canal desligado no público no momento do envio → ninguém recebe (§2.2, §2.3).

### 2.2 `channel: "whatsapp_api"`

```json
{
  "campaign_import_id": 42,
  "channel": "whatsapp_api",
  "campaign": {
    "title": "Renovação — outubro",
    "inbox_id": 9,
    "scheduled_at": null,
    "message_body": "Olá {{contact.first_name}}, da {{contact.company}}!",
    "template_id": 3,
    "company_default": "sua empresa"
  }
}
```

- Usa o criador do motor (`WhatsappApiCampaigns::Creator`): caixa API marcada para campanha, modelo
  salvo da caixa (`template_id`, opcional — o corpo do modelo substitui `message_body`), fuso da
  conta. `scheduled_at: null` = agora.
- **Anexo**: mesmo campo do endpoint antigo, `campaign[media_file]` em `multipart/form-data`
  (mesmos limites de tamanho e tipo).
- Fichas aceitas: `{{contact.name}}`, `{{contact.first_name}}`, `{{contact.company}}` (**nova**, para
  todas as campanhas de WhatsApp API). Leitura e substituição numa passada só, sem regex
  (`CampaignJourney::TemplatePlaceholders`); valor inserido nunca é lido de novo como ficha.
- **D7**: `{{contact.company}}` = nome da empresa ligada ao contato (`contact.company.name`; sem
  Enterprise, `additional_attributes.company_name`). Sem empresa e sem `company_default` → a pessoa
  fica **Pulada** (`status = cancelled`, `last_error_message = "falta empresa"`). Com
  `company_default`, o texto entra no lugar (até 1024 caracteres; quebras de linha viram espaço).
  Fica guardado em `campaign_audience_links.variable_defaults["contact.company"]`.
- Canal WhatsApp desligado no público na hora do envio → todos **Pulados** com
  `"Canal WhatsApp desligado no público"`.
- `audience` da campanha recebe só um marcador `[{ "type": "CampaignAudience", "id": 42 }]` (o model
  exige presença); quem recebe vem do vínculo.

Resposta `200`:

```json
{ "id": 15, "title": "Renovação — outubro", "channel": "whatsapp_api", "scheduled_at": "…", "inbox_id": 9, "recipients_count": 2 }
```

Códigos próprios (`422`): `whatsapp_api_inbox_required` (caixa inexistente ou não marcada),
`template_not_found`, `unsupported_variables` (ficha fora das três), `media_file_too_large`,
`media_file_type_not_supported`.

Depois de criada, a campanha é uma `WhatsappApiCampaign` comum: lista, detalhe, pausar, retomar e
cancelar pelos endpoints de sempre (`/whatsapp_api_campaigns`). Os pulados por empresa aparecem em
`whatsapp_api_campaign_recipients` com o motivo.

### 2.3 `channel: "email"`

```json
{
  "campaign_import_id": 42,
  "channel": "email",
  "campaign": {
    "title": "Novidades de outubro",
    "delivery_mode": "ses",
    "sender_identity_id": 4,
    "from_name": "Hub2You",
    "from_email": "ola@empresa.com.br",
    "reply_to_inbox_id": 12,
    "subject": "opcional",
    "preheader": "opcional"
  }
}
```

- `delivery_mode`: `ses` (domínio verificado: `sender_identity_id`, `from_email` do domínio) ou
  `direct_inbox` (envio pela caixa: `sender_inbox_id`; o "De" é sempre o e-mail da caixa).
- `reply_to_inbox_id`: caixa de **e-mail** da conta (§3). Opcional.
- Cria um **rascunho** (`EmailCampaign`, `status: draft`) ligado ao público e grava os destinatários
  (§2.1) em `email_campaign_recipients` com `contact_id`. Endereço suprimido (descadastro, bounce,
  reclamação) entra como `suppressed` (conta em "não recebem"). A verificação prévia (higiene) é
  enfileirada logo depois.
- Personalização disponível no editor (aparece em `GET …/email_campaigns/campaigns/:id/placeholders`):
  `nome`, `email`, `unsubscribe_url` (de sempre) + `primeiro_nome`, `empresa` (empresa do contato ou
  da planilha) e as **colunas extras do público** com a chave normalizada do importador
  (`Vencimento` → `vencimento`, `Data de Vencimento` → `data_de_vencimento`).
- **O conteúdo não é criado aqui.** Com o `id` retornado, a tela abre o fluxo de e-mail existente:
  `WelcomeChooser` (Criar com IA / Escolher um modelo / Começar do zero) → `AiComposerDialog` ou
  `EmailTemplatesPage` → `EmailBuilderPage` (rota `campaigns_email_builder`, `email_campaigns/:campaignId/builder`) → detalhes do envio.
  Tudo isso usa os endpoints de hoje: `PATCH /email_campaigns/campaigns/:id` (assunto, prévia,
  corpo, remetente, `reply_to_inbox_id`), `POST …/ai/generate`, `GET …/campaigns/:id` (traz `send_readiness`
  e os `checks`), `POST …/send_now`, `POST …/schedule`.
- Subir planilha de destinatários numa campanha ligada a público é recusado:
  `POST …/campaigns/:id/recipients` e `…/recipients/retry_import` → `422 { "error": "email_campaign.audience_linked" }`.
- **Falha fechada**: se o canal e-mail do público for desligado depois do rascunho, a campanha deixa de
  ser enviável (`send_now`/`schedule` → `422 email_campaign.not_sendable`) e a lista de prontidão
  mostra `checks.recipients = false` e `checks.audience_channel = false`. Campanha agendada ou
  enviando segura o canal: desligar responde `422 audience_in_use` (agora vale também para e-mail
  e WhatsApp API; rascunho de e-mail não segura).

Resposta `200`:

```json
{ "id": 31, "title": "Novidades de outubro", "channel": "email", "status": "draft", "delivery_mode": "ses",
  "reply_to_inbox_id": 12, "recipients_count": 1, "suppressed_count": 1 }
```

`recipients_count` = destinatários `pending` (vão receber); `suppressed_count` = não recebem.

O objeto de campanha de e-mail (`show`/`index`/recipients — o mesmo DTO, #436) ganhou só
`reply_to_inbox_id`. O público ligado e o endereço efetivo de resposta não entram no DTO (custariam
uma consulta por campanha na lista): a tela já sabe o público (foi ela que criou a campanha) e o
endereço de resposta segue a ordem do §3.

## 3. Respostas vão para a caixa X (L5)

`EmailCampaigns::ReplyTo` decide o `Reply-To` dos três caminhos (domínio, direto e teste), nesta ordem:

1. `reply_to_inbox_id` da campanha → endereço da caixa de e-mail;
2. `reply_to` digitado (formulário antigo);
3. caixa de respostas do domínio (`email_sender_identities.reply_to_inbox_id`, só envio por domínio);
4. o remetente (`from_email` do domínio; no direto, o e-mail da caixa).

A resposta enviada para o endereço da caixa entra pelo encaminhamento/IMAP dessa caixa e vira
conversa nela, com o contato achado pelo e-mail de quem respondeu (spec com e-mail recebido
simulado). A **marca da campanha** na conversa (K5) é do #1002.

## 4. Enviar teste (D8, L6)

`POST /api/v1/accounts/:account_id/email_campaigns/campaigns/:id/test_send`

- Corpo **vazio** → vai **só para o e-mail do usuário logado** ("Enviar teste para mim").
  `to_email` continua aceito para o campo do editor (comportamento de antes).
- Envio por domínio: pelo SES; envio direto: **pela caixa** da campanha. Mesmo `Reply-To` do envio real.
- Amostra: primeiro destinatário (fichas preenchidas com os dados dele); link de descadastro inerte (`#`);
  sem `List-Unsubscribe`.
- Não cria destinatário nem evento: **não conta no resultado**.
- `200 { "message_id": "…", "to_email": "gestora@empresa.com.br" }`
- `422`: `email_campaign.invalid_email`, `email_campaign.sender_identity_missing` (domínio não
  verificado/ausente), `email_campaign.sender_inbox_missing` (direto sem caixa de e-mail),
  `email_campaign.test_send_failed` (a caixa não conseguiu enviar; o motivo do provedor não é exposto),
  ou a mensagem do SES.

## 5. Resultado do e-mail (E1)

`CampaignJourney::EmailResultTotals.new(campaign).call` →
`{ eligible:, delivered:, bounced:, not_sent: }`, com `delivered + bounced + not_sent = eligible`:

| grupo | regra em `email_campaign_recipients` |
|---|---|
| Voltaram | `status = bounced` |
| Entregues | não `bounced` e `sent_at` presente (entregue, aberto, clicado, descadastrou/reclamou depois, ou só aceito) |
| Não enviados | não `bounced` e `sent_at` nulo (suprimido, falhou, cancelado, pendente) |
| Público elegível | todos os destinatários da campanha (`recipients_count`) |

WhatsApp API: `sent_count + failed_count + cancelled_count = recipients_count` (pulados por recusa,
por "falta empresa" ou por canal desligado estão em `cancelled`).

## 6. O que continua igual (§6.9, L1–L4)

Specs com campanha **ligada a público** em
`spec/requests/api/v1/accounts/campaign_journey/email_campaigns_spec.rb`: cada trava da prontidão
(assunto, conteúdo, remetente, destinatários, importação, higiene, provedor), bloqueio de
reputação do provedor (bounce 5%, reclamação 0,1%, dado desconhecido bloqueia, com o motivo),
rodapé de descadastro travado + `List-Unsubscribe` one-click, e envio direto (horário comercial,
teto diário da caixa, pausa automática).
