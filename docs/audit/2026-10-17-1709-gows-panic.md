# #1709: causa raiz dos panics do GOWS no teste real (17/10/2026)

Investigação só de leitura. Nada foi enviado pelo WhatsApp, o container não foi parado nem reiniciado, o volume não foi alterado (os bancos foram copiados com `docker cp` para `/tmp` no M2, lidos com `sqlite3 -readonly` e apagados em seguida) e produção não foi tocada.

## Ambiente (fatos)

- Motor `waha-c2y-teste1709`, imagem `autonomia-waha-c2y-rich:2026.9.2-c2y-rich-5`, **linux/amd64** (`PLATFORM="linux/amd64"` fixo em `infra/waha-c2y/build-waha-c2y-rich.sh:55`).
- O M2 roda colima **aarch64** (`docker info`: `aarch64`, kernel 6.8.0-117). O amd64 roda por **QEMU user-mode**: `binfmt_misc/qemu-x86_64`, interpretador `/usr/bin/qemu-x86_64`, **versão 7.0.0** (2022). Não é Rosetta.
- GOWS: binário Go 1.26 (stack mostra `mgcmark_greenteagc.go`), `google.golang.org/protobuf v1.36.12`. O código-fonte do gows-plus no scratchpad (`gows-src/x/devlikeapro-gows-plus-8179447`, `go 1.26.0`, protobuf v1.36.12) bate com os caminhos e as linhas do stack (`message_mapper.go:117` e `:154`).

## Causa, com evidência

### 1. Os panics não dependem do dado gravado

- **`message_mapper.go:117`** é `json.Unmarshal(data, &temp)` para uma struct simples (`messageTemp`, com 3 `json.RawMessage`). `RawMessage.UnmarshalJSON` testa `m == nil` e faz `append`; o receptor do stack é não nulo (`0xe0e174769e0`). Com JSON válido, um SIGSEGV dentro dessa função não acontece num runtime íntegro.
- **`desc_lazy.go:438`** (protobuf v1.36.12) é a inicialização preguiçosa do **descritor compilado** do `waE2E.proto`. A entrada é constante do binário, não vem do banco. O panic dispara quando um `Field` recém-alocado já tem `ContainingOneof != nil`, ou seja, **memória nova que não veio zerada**:

```go
od.L1.Fields.List = append(od.L1.Fields.List, fd)
if fd.L1.ContainingOneof != nil {
    panic("oneof type already set")
}
```

  Esse panic aconteceu ao ler uma mensagem de **texto**, não a enquete.
- O `fatal error` das 06:02:06 é o GC encontrando, num objeto de 8 KiB, um ponteiro para uma região livre. Os campos desse objeto (`*(object+24) = 0xe0e16ee1860`, `*(object+32) = 0x1647020`) são o mesmo `*filedesc.File` (`0xe0e16ee1860`) cujo init quebrou às 06:01:40. É a mesma estrutura corrompida.

São três sintomas diferentes, em três bibliotecas (protobuf, encoding/json e GC), em mensagens diferentes e na mesma janela de 26 s. Isso é **corrupção de heap**, não um bug determinístico de leitura de enquete.

### 2. Hipótese principal (forte, ainda não reproduzida): QEMU 7.0 linux-user + `MADV_DONTNEED`

- O Go no Linux devolve páginas com `madvise(MADV_DONTNEED)` e **conta com elas voltando zeradas**. O QEMU linux-user historicamente ignorava `MADV_DONTNEED` e, desde a correção parcial de 2022, só repassa ao host em casos estreitos (faixa anônima alinhada à página do host). Fora disso, a página fica com o dado velho ([qemu#326](https://gitlab.com/qemu-project/qemu/-/issues/326), [patch "partial support for MADV_DONTNEED"](https://git.linaro.org/plugins/gitiles/people/peter.maydell/qemu-arm.git/+/892a4f6a750abceeda4c1ee8324f58f82fd6bd89%5E%21/linux-user/syscall.c)).
- O relato aberto [qemu#4654](https://gitlab.com/qemu-project/qemu/-/work_items/4654) mostra binários Go sob qemu-user com **"found bad pointer in Go heap"**, "marked free object in span" e SIGSEGV em `memmove`, o mesmo quadro daqui. `GODEBUG=madvdontneed=0` faz sumir (15/20 quedas contra 0/20). Lá é qemu-aarch64 10.2.3 em host x86, o caminho inverso do nosso, mas o mecanismo é o do `target_madvise` do linux-user. Há relatos antigos parecidos com Go sob emulação qemu ([golang/go#35254](https://golang.org/issue/35254)).
- "Memória nova não zerada" é exatamente o que o panic `oneof type already set` exige.
- Os registros não provam que foi este o mecanismo. Para provar é preciso o teste A/B descrito em "Como reproduzir".

### 3. Consequência agravante: bug real do protobuf-go, que só aparece depois da corrupção

`filedesc.(*File).lazyInitOnce` (protobuf v1.36.12, `internal/filedesc/desc.go:169-176`) faz `fd.mu.Lock()` **sem `defer` Unlock**. O panic de 06:01:40 deixou esse mutex **travado para sempre**. No dump da queda há 3 goroutines (`handleReceipt`) paradas em `sync.Mutex.Lock` em `desc.go:170`, no mesmo `File 0xe0e16ee1860`.

Daí em diante, toda leitura de mensagem guardada que passa por `protojson` (recibos, decifrar o voto, que busca a enquete no banco) **fica pendurada**. Isso explica por que o voto feito no celular não chegou ao chat2you até o motor reiniciar e por que ele chegou às 06:04:27.

### 4. A queda das 05:55:40 (exit 143)

Não há stack, não há "SIGTERM received" e não há "GOWS stopped" antes dela, e o "POST …/start" citado é só o contexto de trace. Os registros **não mostram a causa**. Na queda 2, o caminho registrado foi: GOWS morre → Node se encerra com SIGTERM → exit 143. Uma queda do GOWS (ou do próprio qemu) sem o stderr chegar ao log daria o mesmo exit 143, mas isso é hipótese sem prova. Ela aconteceu 14 s depois de um `sendVoice` e da conversão de mídia (alocação grande), o que é compatível com a mesma corrupção.

## Respostas

1. **Mesma causa?** Os dois panics e o `fatal error` têm a mesma origem provável: o heap corrompido do processo GOWS. Não é o mesmo ponto: o 1º foi em `message_mapper.go:154`/protobuf, numa mensagem de texto, e o 2º em `:117`/encoding/json, na enquete. A queda de 06:02:06 **não** foi um panic na sessão A ao decifrar o voto. Foi o GC achando um ponteiro inválido, e isso derruba o processo inteiro. O voto chegou depois do reinício. A queda de 05:55:40 ainda não tem causa provada; ela é compatível com a mesma hipótese.
2. **Linha 117 e campo:** nenhum campo do JSON é nulo nem inválido. O JSON gravado é válido e tem o formato padrão nas duas sessões (tabela acima). O nil pointer aconteceu dentro de `RawMessage.UnmarshalJSON` com receptor válido, o que é sintoma de memória corrompida e não de dado.
3. **Bug do GOWS oficial ou do nosso conector?** Nenhum dos dois, pela evidência. O conector manda só `name`, `options` e `multipleAnswers` (`app/services/waha/client/rich_sends.rb:24`, `BuildWahaNativeRequest` no patch), mais o `id` determinístico `3EB0`+18 hex, que tem o formato do WhatsApp Web. Quem monta a enquete é o próprio GOWS (`server/messages.go:194`, `BuildPollCreationV3`) e gera o `messageSecret`. Uma enquete feita no celular passa pelo mesmo `MessageMapper.Marshal/Unmarshal`. O panic 1 nem envolveu enquete. **Não há indício de que a waha-plus pura em amd64 nativo tenha esse problema.** Ainda falta confirmar isso em produção, só por leitura (ver abaixo).
4. **Derruba o motor todo?** O `fatal error` (corrupção detectada pelo GC) derruba o processo GOWS inteiro, e com ele o Node e todas as sessões do container (`Stopping all sessions...`). Os panics "comuns" são recuperados, mas o 1º deixou o mutex do protobuf travado, o que congela a leitura de mensagens guardadas em **todas** as sessões do processo. Para produção (wa-hub, wa-autonomia): se os hosts forem amd64 nativos, a hipótese não se aplica e nada aqui sugere que um voto derrube o motor. Isso não foi verificado nesta investigação, porque produção não foi tocada.
5. **Correções:**
   - (a) Conector/payload: não há o que corrigir. O payload é o documentado e o GOWS monta a mensagem.
   - (b) GOWS: o código do gows-plus está disponível (`devlikeapro-gows-plus-8179447`). O defeito real é o `lazyInitOnce` sem `defer` no **protobuf-go** (upstream), que só importa depois de uma corrupção. Não há o que pedir à devlikeapro por esta evidência. O changelog/issues do WAHA não foram consultados a fundo, porque a causa não aponta para eles.
   - (c) Proteção no patch JS para evitar o caminho: **não recomendo**. Seria contornar um sintoma de emulação.
   - **Recomendado:** parar de validar GOWS sob emulação qemu. Rodar a imagem **nativa arm64** no M2, ou amd64 num host amd64 real (o canário). Como mitigação só para o teste emulado, `GODEBUG=netdns=cgo,madvdontneed=0` (mantendo o `netdns=cgo` que a imagem já usa).

## (b) Imagem arm64

- A WAHA **core** pública publica arm como **tag separada**, não como manifest multi-arch: `devlikeapro/waha:gows` → só linux/amd64, `devlikeapro/waha:gows-arm` e `:arm` → linux/arm64 (conferido com `docker buildx imagetools inspect`).
- A **waha-plus** é privada: sem login, o registry recusa (`insufficient_scope`). **Não consegui conferir** se existe `2026.9.2` arm64 nem o digest dela. O provável, pelo padrão da core, é uma tag `-arm` separada. Para conferir, alguém com a credencial do Plus roda `docker buildx imagetools inspect devlikeapro/waha-plus:<tag>-arm` (sem pull).
- O overlay é só JS (`/app/dist`), então dá para montar a c2y-rich-5 sobre a base arm64. Mudanças no `build-waha-c2y-rich.sh`:
  1. `PLATFORM="${WAHA_C2Y_PLATFORM:-linux/amd64}"` em vez do valor fixo (linha 55). O resto já usa `$PLATFORM`: `docker create --platform`, a checagem `base_platform`, o `buildx --platform` e a checagem final.
  2. O passo 1 (hash dos 25 JS originais da base) passa a valer como prova de que o `dist` arm64 é idêntico ao revisado. Se algum hash divergir, o script já recusa.
  3. O builder de `dist` roda Node nativo e gera JS neutro de arquitetura, então não muda. Já o tag e o `.sha256` precisam do sufixo da arquitetura (ex.: `…-c2y-rich-5-arm64`), para não se confundirem com a imagem de produção.
  4. O smoke passa a rodar nativo no M2, sem `WAHA_C2Y_SKIP_SMOKE`.

## Como reproduzir com segurança

Nada de números reais. Os números do Rodrigo e as caixas de clientes ficam de fora.

1. **Sem WhatsApp:** o panic 1 não depende de rede, só de `protojson` + alocação. Monte um binário Go 1.26 que faça em laço `protojson.Unmarshal` de um `waE2E.Message` (com a mensagem de enquete do formato acima) e, em paralelo, gere pressão de memória (`GOGC=1`, `GOMEMLIMIT=…`). Rode três vezes em `--platform linux/amd64`: (i) emulado no M2, (ii) emulado com `GODEBUG=madvdontneed=0`, (iii) nativo arm64 no M2 e/ou num host amd64 real. A hipótese se confirma se só (i) quebrar.
2. **Com WhatsApp:** dois números de teste descartáveis, motor nativo (arm64 no M2 ou amd64 real), enquete via chat2you, voto pelo celular e `sendPollVote`, repetido N vezes. Esperado: nenhum panic.

## Pendências (precisam de OK do Rodrigo, porque são leitura em produção)

- `uname -m` / arquitetura dos hosts dos motores wa-hub e wa-autonomia.
- `docker logs <motor> 2>&1 | grep -c -E "found bad pointer|oneof type already set|Panic happened"` nos motores de produção, para confirmar que é zero.
