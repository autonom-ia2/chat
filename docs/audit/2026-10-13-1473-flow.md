# #1473 P2: Flow (formulário do WhatsApp) pelo painel (13/10/2026)

Decisões aprovadas pelo Rodrigo em 13/10/2026, levadas pela coordenação da #1473.

## Contrato

`POST /api/v1/accounts/:account_id/conversations/:id/messages`

```json
{
  "content": "Para seguir com a proposta, entre com seus dados.",
  "content_attributes": {
    "rich_message": {
      "type": "flow", "flow_id": "1234567890", "cta": "Iniciar",
      "token": "<user_session_id>-<timestamp>-<6 dígitos>", "screen": "LOGIN",
      "data": { "produto": "auto" },
      "mode": "draft", "header": "Proposta GTA", "footer": "Leva um minuto", "name": "Login do corretor"
    }
  }
}
```

O que sai para a Meta (Graph `WHATSAPP_API_VERSION`, padrão v22.0, o mesmo ramo do botão de link):

```json
{
  "messaging_product": "whatsapp", "recipient_type": "individual", "to": "5511...", "type": "interactive",
  "interactive": {
    "type": "flow",
    "header": { "type": "text", "text": "Proposta GTA" },
    "body": { "text": "Para seguir com a proposta, entre com seus dados." },
    "footer": { "text": "Leva um minuto" },
    "action": {
      "name": "flow",
      "parameters": {
        "flow_message_version": "3", "flow_token": "<token>", "flow_id": "1234567890", "flow_cta": "Iniciar",
        "flow_action": "navigate", "flow_action_payload": { "screen": "LOGIN", "data": { "produto": "auto" } },
        "mode": "draft"
      }
    }
  }
}
```

| Campo | Obrigatório | Regra |
|---|---|---|
| `content` | sim | de 1 a 1024 caracteres, medidos no texto que sai de fato |
| `flow_id` | sim | texto em uma linha (número em JSON é recusado: a Meta espera texto) |
| `cta` | sim | texto do botão, de 1 a 30 caracteres, em uma linha |
| `token` | sim | texto em uma linha; o formato é de quem envia, o painel não o confere |
| `screen` | sim | tela inicial, texto em uma linha |
| `data` | não | objeto com ao menos um campo; vai como veio para a primeira tela |
| `mode` | não | só `"draft"`; sem ele, sai o formulário publicado |
| `header` / `footer` | não | texto de até 60 caracteres, em uma linha |
| `name` | não | nome legível para a conversa do atendente; texto em uma linha; não vai para a Meta |

Fixos: `flow_action: navigate` e `flow_message_version: "3"`. Ficaram de fora, por decisão: `data_exchange` e
`flow_name`.

**Limites, fato e inferência.** Fato (guia "Sending a Flow" da Meta,
https://developers.facebook.com/docs/whatsapp/flows/guides/sendingaflow): `flow_message_version` "3"; `flow_id` ou
`flow_name`, nunca os dois; `flow_cta` com recomendação ("advised") de até 30 caracteres, sem emoji; `flow_action`
`navigate` ou `data_exchange`; `data`, se vier, objeto não vazio; `mode` `draft` ou `published`. **Não confirmado
para o Flow:** corpo até 1024 e cabeçalho/rodapé até 60. A Meta não publica esses números para o Flow; vêm do botão
de link e dos limites de modelo, adotados aqui para o mesmo pedido ter o mesmo resultado. O guia só mostra
cabeçalho de texto; cabeçalho de mídia ficou fora. Emoji no `cta` não é recusado pelo painel (é recomendação).

## Onde o Flow sai

O Flow não tem versão em texto (`def self.text_version? = false`). Comportamento lido no código comum do P1, sem
alteração:

| Canal | Resultado |
|---|---|
| WhatsApp oficial, janela aberta | `interactive`/`flow` |
| WhatsApp oficial, janela fechada | `failed` com o erro de janela (`RichMessages.window_error`) |
| WhatsApp oficial com Híbrido, janela fechada ou 131047 | não sai pelo WAHA (`router.rb` consulta `RichMessages.text_capable?`, falso); `failed` |
| Qualquer outro canal (360dialog, Telegram, caixa API, e-mail, widget...) | 422 na criação pela API; `failed` no envio (`NO_TEXT_VERSION`) |

## Dados iniciais (`data`): limite aceito

Opção (a), aprovada: a bolha do atendente não lê nem desenha `data` (nem o `token`), e `rich_message` já sai
filtrado do log de parâmetros. Nada é cifrado.

**Limite:** `data` fica gravado em `content_attributes` e por isso chega, como qualquer chave dali, a:
- webhooks da conta e AgentBot (`Message#webhook_data`), em `message_created` e em todo `message_updated`;
- ActionCable do painel (`Message#push_event_data`, com `previous_changes` no `message_updated`), ou seja, ao
  navegador do atendente, sem aparecer na tela;
- API de mensagens (`app/views/api/v1/models/_message.json.jbuilder`);
- o reenvio, que mantém o `rich_message` inteiro.

Por isso **`data` nunca deve levar credencial nem dado pessoal**. A retirada dos valores de login fixos do nó `Flow`
do `gta_api_proposal` é da coordenação da #1473, fora desta entrega.

## Falha da Meta: como o n8n descobre (nada muda no painel)

Recusa de formato volta na hora: 422 na criação. Depois de criada, toda falha grava `content_attributes.external_error`
e dispara `message_updated` (webhooks da conta e AgentBot):
- recusa da Meta no envio (`Whatsapp::Providers::BaseService#handle_error`);
- trava do módulo e erro de montagem (`RichMessages.fail!`);
- janela fechada (`Whatsapp::SendOnWhatsappService`);
- falha que chega depois pelo status da Meta (`Messages::StatusUpdateService`).

**Sinal para o n8n:** evento `message_updated` com o `id` da mensagem criada (devolvido na criação) e
`content_attributes.external_error` preenchido; `content_attributes.rich_message.token` serve de conferência. O
`webhook_data` **não traz `status`**: o sinal é o `external_error`. Não conferido: se o webhook da conta usado pelo
n8n assina `message_updated` (configuração de produção).

## A resposta do cliente

Não muda: o `nfm_reply` continua tratado no recebimento (`config/initializers/autonomia_whatsapp_flows_nfm_reply.rb`,
que grava `content_attributes.flow_response` com o `flow_token`) e na bolha `WhatsappFlowResponse`. Esta entrega só
toca o envio.

## Conversa do atendente

`types/Flow.vue`: corpo, cabeçalho e rodapé pelo `Frame`, o botão com o `cta` como o cliente vê (sem link: o
atendente não abre o formulário) e a linha "Formulário enviado: <nome>" ("Formulário enviado" sem `name`).
