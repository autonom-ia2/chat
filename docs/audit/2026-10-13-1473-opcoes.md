# #1473 P3: opções (botões de resposta e lista) pelo painel (13/10/2026)

## Contrato

`POST /api/v1/accounts/:account_id/conversations/:id/messages`

Botões (até 3 opções soltas, sem descrição):

```json
{
  "content": "Recebi seus dados. Como você prefere continuar?",
  "content_attributes": {
    "rich_message": {
      "type": "options", "header": "Próximo passo", "footer": "Toque em uma opção.",
      "options": [
        { "id": "agendar", "title": "Agendar visita" },
        { "id": "horarios", "title": "Ver horários" },
        { "id": "pessoa", "title": "Falar com uma pessoa" }
      ]
    }
  }
}
```

Lista (com seções, ou mais de 3 opções, ou alguma descrição):

```json
{
  "content": "Escolha o assunto para eu te ajudar melhor.",
  "content_attributes": {
    "rich_message": {
      "type": "options", "header": "Assuntos", "button": "Ver assuntos",
      "sections": [
        { "title": "Atendimento", "options": [
          { "id": "remarcar", "title": "Remarcar horário", "description": "Trocar o dia ou a hora" },
          { "id": "cancelar", "title": "Cancelar horário" }
        ] },
        { "title": "Pagamento", "options": [{ "id": "boleto", "title": "Segunda via do boleto" }] }
      ]
    }
  }
}
```

- `options` OU `sections` (nunca os dois). Cada opção: `id` (texto, obrigatório, único na mensagem), `title`
  (texto, obrigatório, uma linha), `description` (opcional).
- **Botões ou lista é decidido pelo painel:** lista quando vêm `sections`, mais de 3 opções ou alguma
  `description` (o botão de resposta não mostra seção nem descrição); senão, botões. O robô não precisa saber.
- `header` e `footer`: opcionais, texto de até 60 caracteres, em uma linha. Só cabeçalho de **texto**.
- `button`: o texto do botão que abre a lista, até 20 caracteres, em uma linha. **Obrigatório quando o envio vira
  lista** (sem ele: 422 na criação pela API e `failed` no envio, com `LIST_BUTTON_INVALID`). Nos botões é ignorado,
  nem validado. O painel não inventa esse texto: ele vai ao cliente, e o painel não sabe o idioma da conversa.
  Quem não sabe se vira lista pode mandar `button` sempre.
- O corpo (`content`) é obrigatório.

### Limites (validados antes do envio, motivo legível em constante do tipo)

Conferidos nas páginas oficiais da Meta em 13/10/2026
([botões](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/interactive-reply-buttons-messages),
[lista](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/interactive-list-messages)).

| | Botões | Lista |
|---|---|---|
| Opções | 1 a 3 | 1 a 10 no total, em 1 a 10 seções |
| Título da opção | 20 | 24 |
| `id` da opção | 256 | 200 |
| Descrição | (vira lista) | 72 |
| Corpo | 1024 | 4096 |
| Cabeçalho de texto / rodapé | 60 / 60 | 60 / 60 |
| Botão da lista | não se aplica | 20 |
| Título da seção | não se aplica | 24; obrigatório com mais de uma seção; seção única sem título sai com o `button` |
| Repetição | `id` e título não se repetem | `id` não se repete |

O título único dos botões está escrito na página da Meta ("Must be unique if using multiple buttons"). O `id`
único é regra nossa (a resposta do cliente é identificada por ele).

Trechos conferidos em 13/10/2026:

- **Corpo da lista, 4096:** página da lista, campo do corpo: "Message body text. Supports URLs." / "Maximum 4096
  characters."
- **Título de seção com mais de uma seção:** a página da lista diz só "Section title text. At least 1 section is
  required. Supports up to 10 sections." / "Maximum 24 characters.", sem falar de obrigatoriedade. A
  [referência de mensagens da Cloud API](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages),
  no objeto de seção, diz: "Title of the section. Required if the message has more than one section. Max 24
  characters." As duas páginas foram lidas por ferramenta de busca, que devolve o texto resumido; os trechos acima
  vieram pedidos literalmente.
- **Decisão (2ª revisão):** para não arriscar a recusa pela leitura mais estrita (a página atual lista o título sem
  condição), **toda seção sai com título**. Com mais de uma seção, o chamador manda o de cada uma (sem ele: 422,
  `SECTION_TITLE_INVALID`). A seção única sem título, tanto a das opções soltas que viram lista quanto a que o
  chamador mandou sem título, sai com o texto do `button`, que é obrigatório na lista e cabe (20 de 24). Seção única
  com título sai com o título dado.
- **Contagem de caracteres:** a Meta não define se os limites contam *code points*, unidades UTF-16 ou grafemas. O
  painel conta *code points* (`String#length` do Ruby). Emoji composto (família, bandeira) pode contar diferente lá;
  **a confirmar no teste real**.
- **Uma linha só:** título e descrição da opção, cabeçalho, rodapé, botão da lista e título de seção recusam `\n`, `\r`, tabulação
  vertical (`\v`), U+0085, U+2028 e U+2029, por lista constante (`LINE_BREAKS`), sem regex. Mesmo critério do P5.

### O que vai à Meta

Botões: `interactive` / `button`, `action.buttons[] = { type: "reply", reply: { id, title } }`.
Lista: `interactive` / `list`, `action = { button, sections: [{ title, rows: [{ id, title, description? }] }] }` (toda seção
com título).
Corpo e opções na mesma mensagem.

### Versão em texto (canal sem formato interativo)

Corpo, uma linha em branco e as opções numeradas, uma por linha; título da seção numa linha própria; descrição
depois de " - ". Cabeçalho, rodapé e botão da lista não entram (moldura do cartão, como no botão de link).

```
Escolha o assunto para eu te ajudar melhor.

Atendimento
1. Remarcar horário - Trocar o dia ou a hora
2. Cancelar horário
Pagamento
3. Segunda via do boleto
```

Onde o texto de saída é HTML (Telegram), as opções vão escapadas. Os canais seguem a tabela do botão de link
(`2026-10-13-1473-botao-de-link.md`): o tipo tem versão em texto, então e-mail e chat do site recusam, e o
WhatsApp oficial fora da janela falha com o erro de janela (ou sai em texto pelo Híbrido).

## Resposta do cliente: `selected_option`

Quando o cliente toca num botão de resposta, numa linha de lista ou num botão de resposta rápida de modelo, a
mensagem recebida guarda, além do título em `content` (como o Chatwoot já fazia):

```json
"content_attributes": {
  "in_reply_to": 4211,
  "in_reply_to_external_id": "wamid.da-mensagem-das-opcoes",
  "selected_option": { "id": "remarcar", "title": "Remarcar horário" }
}
```

Sem título na resposta (ou título vazio), grava só o `id` (`{ "id": "remarcar" }`): nunca `title` vazio. A bolha, aí,
usa o título da opção oferecida com esse `id`.

- `in_reply_to` / `in_reply_to_external_id` já eram gravados pelo Chatwoot a partir do `context.id` da Meta.
- Vale para **qualquer** botão ou lista: `options`, o `input_select` antigo (mesmos `button_reply` / `list_reply`)
  e os botões de resposta rápida de modelo (`button.payload` vira o `id`, `button.text` o `title`).
- Webhook do robô: `content_attributes` vai inteiro (`Message#webhook_data`); o agente lê na mensagem.
- Payloads de origem (Meta, webhook `messages`): `interactive.button_reply = { id, title }`,
  `interactive.list_reply = { id, title, description }`, `button = { payload, text }`.

Implementação: `RichMessages::SelectedOption`, prepend em `Whatsapp::IncomingMessageBaseService` pelo initializer
próprio `config/initializers/rich_messages_selected_option.rb`. Sobrescreve só `message_content_attributes`
(do Chatwoot, conferido com `git blame`), chamando `super` e acrescentando a chave. Não toca `create_message`, a
escolha da conversa nem quem responde (área do #1433). Vale para o WhatsApp oficial e o 360dialog, que herdam a
mesma base.

## O atendente vê

Bolha `types/Options.vue` (com `OptionsList.vue` e `optionsAnswer.js` fora de `types/`), como o protótipo
aprovado: botões, ou a lista sempre aberta com seções e descrições, com o texto do botão exatamente como foi
enviado; embaixo, "O cliente tocou em …" quando a resposta é achada. **Sem resposta achada, não há linha
nenhuma**: a bolha só enxerga as mensagens carregadas, então não pode afirmar que o cliente não escolheu (o
protótipo mostrava "O cliente ainda não escolheu"; saiu na revisão).

**Como a bolha sabe qual foi tocada.** A resposta é outra mensagem. A bolha percorre as mensagens da conversa
aberta na loja (`getSelectedChat`) do fim para o começo e para na primeira de entrada com `in_reply_to` igual ao
id da mensagem das opções e com `selected_option` (a mais recente). Nada é gravado na mensagem enviada (o
protótipo lia `submitted_values` nela, mas ninguém gravaria esse campo sem mexer no recebimento de outra forma).
Nenhum arquivo comum foi editado.

**Título da escolha.** O título da opção oferecida com o `id` tocado; se ela não estiver na mensagem, o título que
veio na resposta; sem nenhum dos dois, não há linha. A bolha acompanha a loja: resposta que chega depois (websocket)
faz a linha aparecer.

**Título da seção na bolha: o que saiu.** A seção única sem título aparece com o texto do `button`, igual ao que foi
à Meta. A bolha é espelho do que o cliente recebeu (decisão aprovada); mostrar sem título seria mostrar algo que o
cliente não viu, e o atendente não teria como entender o cabeçalho que aparece no celular do cliente.

**Acessibilidade.** A bolha é espelho do que o cliente recebeu e nada nela é tocável nem focável no painel; um
texto só para leitor de tela diz isso ("Cópia do que o cliente recebeu. Só o cliente pode tocar nestas opções.").
Cada seção da lista é um grupo (`role="group"`) com o nome da seção.

## Decisões

- **Lista ou botões decidido pelo painel**, pela regra acima; a bolha usa a mesma regra.
- **`id` só em texto**: número é recusado (a Meta pede texto e o robô compara texto com texto).
- **Sem texto padrão para o botão da lista** (revisão): a primeira versão mandava `Ver opções` fixo em português,
  um texto de sistema sem o idioma da conta. Agora `button` é obrigatório na lista e a bolha mostra o que foi
  enviado.
- **`input_select` não mudou**: o envio dele (`content_type: input_select` + `items`) segue nos provedores; a trava
  recusa `rich_message` com `content_type` diferente de texto.

## Fora desta entrega

- **Cabeçalho de imagem** nas opções: a trava atual recusa `rich_message` com anexo, e o protótipo não cobriu a
  tela. Cabeçalho que não é texto é recusado com `HEADER_INVALID`.
- Resposta por número em canal de texto ("2") não vira `selected_option`; nesses canais a bolha fica sem a linha
  da escolha.
- A bolha só acha a resposta entre as mensagens carregadas na conversa aberta; fora delas, fica sem a linha.
- Nenhum envio real à Meta: tudo com WebMock. Prova real na conta 16 depois do deploy.
