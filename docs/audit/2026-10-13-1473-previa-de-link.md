# #1473 P6: prévia de link pelo painel (13/10/2026)

## Contrato

`POST /api/v1/accounts/:account_id/conversations/:id/messages`

```json
{
  "content": "Sua proposta está pronta: https://exemplo.com.br/p/42",
  "content_attributes": { "rich_message": { "type": "link_preview" } }
}
```

No WhatsApp oficial, com a janela aberta, sai para a Meta (Graph `WHATSAPP_API_VERSION`, padrão v22.0):

```json
{
  "messaging_product": "whatsapp", "recipient_type": "individual", "to": "5511...",
  "type": "text",
  "text": { "body": "Sua proposta está pronta: https://exemplo.com.br/p/42", "preview_url": true }
}
```

Com `context: { message_id }` quando a mensagem responde a outra (o ramo do módulo já monta; coberto no spec).

- `content`: até 4096 caracteres, medidos no texto que sai de fato (depois da formatação do canal), com pelo
  menos um endereço que começa com `http://` ou `https://` (em qualquer caixa). O **primeiro** endereço do texto
  é o que vale: se ele não for completo, a mensagem é recusada, mesmo que outro endereço depois dele seja.
  Link em markdown conta. `[texto](https://...)`, `<https://...>` e `**https://...**` são aceitos no WhatsApp
  (sai o endereço puro, ou entre `*`) e no Telegram (sai HTML: `<a href="...">`, `<strong>`), cobertos no spec.
  No Telegram isso vale porque o candidato é cortado no primeiro `"`, `<` ou `>` (ver Decisões), não porque a
  validação leia o texto do WhatsApp: ela lê o texto renderizado do canal da conversa.
- Nenhum outro campo. O endereço é o do corpo, e a Meta não aceita escolher outro: a prévia é sempre do
  **primeiro** endereço do texto. Um campo `url` separado só criaria um segundo lugar para o mesmo dado, que
  poderia divergir do corpo.

Formato inválido responde 422 na criação pela API e fica `failed` com o motivo no envio, pelas regras comuns do
módulo (`RichMessages.format_error`). Motivos do tipo: `NO_WEB_ADDRESS` (nenhum endereço http(s), inclusive corpo
vazio), `INVALID_FIRST_ADDRESS` (o primeiro endereço não é completo) e `BODY_TOO_LONG`.

| Canal | O cliente recebe |
|---|---|
| WhatsApp oficial, janela aberta | `text` com `preview_url: true` |
| WhatsApp oficial, janela fechada | nada; `failed` com o erro de janela, igual ao texto comum |
| WhatsApp oficial com Híbrido, janela fechada | o corpo, em texto |
| WhatsApp 360dialog, Twilio, Telegram, Instagram, Messenger, SMS, Line; caixa API | o corpo, em texto |
| E-mail e chat do site | recusado, como todo `rich_message` (`RichMessages::UNSUPPORTED_CHANNELS`); coberto no spec |

As regras do corpo valem em todo canal que aceita o formato, para o mesmo pedido ter o mesmo resultado.

## Fonte (documentação da Meta, lida em 13/10/2026)

`.../whatsapp/messages/text-messages`: `type: text`, `text: { body, preview_url }`; corpo até 4096 caracteres;
`preview_url: true` faz o aplicativo do cliente **tentar** mostrar a prévia; só o primeiro endereço do corpo;
endereço precisa começar com `http://` ou `https://`; sem `preview_url`, ou se a prévia não puder ser obtida, o
cliente vê o link clicável. A página `.../link-previews` não carregou (o conteúdo veio vazio na leitura), então
regras da miniatura (tags Open Graph, tamanho da imagem) não foram confirmadas na fonte oficial.

## Decisões

- **Arquivo novo só** (`app/services/rich_messages/types/link_preview.rb`). Nenhum arquivo comum tocado.
- **Versão em texto em branco**: nos canais de texto (tabela acima) sai só o corpo, que já tem o endereço. Por
  isso o tipo tem versão em texto (`text_version?` padrão), e com a janela fechada o WhatsApp oficial se comporta
  como o texto comum (erro de janela, ou o Híbrido leva o corpo). E-mail e chat do site continuam recusados.
- **Endereço achado sem regex**: o corpo é quebrado em palavras (`String#split`); a primeira palavra que tem
  `http://` ou `https://` (procurado com `String#index` na palavra em minúsculas ASCII, então `HTTPS://` também
  conta) é o candidato, do esquema até o fim da palavra, sem a pontuação que fecha a frase (`.`, `,`, `;`, `:`,
  `!`, `?`, `)`, `]`, `}`, `'`, `…`, e os marcadores do WhatsApp `*`, `_`, `~`), tirada com `String#chop`.
  Antes de quebrar, os espaços U+00A0, U+202F e U+3000 viram espaço comum (`String#tr` com lista constante).
- **Corte em `"`, `<` e `>`**: esses caracteres nunca aparecem sem escape num endereço (RFC 3986), então marcam
  onde ele acabou. No texto HTML do Telegram é o fim do `href="..."` ou o começo de uma tag; no WhatsApp, aspas
  em volta do endereço. Sem o corte, `<a href="https://exemplo.com.br">proposta</a>` virava o host
  `exemplo.com.br">proposta<` e a mensagem era recusada por engano.
- **Só o primeiro candidato decide**, porque a Meta só faz a prévia dele. Válido, a mensagem sai; inválido, é
  recusada com `INVALID_FIRST_ADDRESS`, mesmo que haja um endereço válido depois: aceitar mandaria uma prévia que
  não aparece, em silêncio.
- **Esquema e host pelo `Addressable::URI`, depois de normalizar**, como no botão de link: esquema em minúsculas
  (`HTTPS://EXEMPLO.COM.BR` é aceito, como no `link_button`), domínio com acento em punycode. O esquema precisa
  ser `http` ou `https`. Entrada que o `Addressable` não consegue ler (porta que não é número,
  `https://exemplo.com.br:abc`; confirmado que lança `InvalidURIError`) é endereço inválido.
- **Host com conteúdo real**: pelo menos duas partes não vazias separadas por ponto (`host.split('.', -1)`), sem
  lista de domínios. Recusa `https://.`, `https://exemplo..com.br` e nome de uma parte só (`localhost`, que o
  aparelho do cliente nunca alcança). IPv4 (`192.168.0.10`) passa pela mesma regra; IPv6 entre colchetes não
  passa. Não se confere a extensão do domínio: isso é lista de palavras, e a Meta não publica uma.
- **Sem bolha nova**: para o atendente a mensagem é texto comum com o link. O `registry.js` devolve `null` para
  tipo sem arquivo em `types/`, e a bolha de texto de sempre mostra o corpo (com o link clicável). Nenhum texto
  novo nos catálogos.

## Graph v22.0 (este tipo) e v13.0 (texto comum)

O ramo do módulo envia pela versão de `WHATSAPP_API_VERSION` (padrão v22.0); o texto comum continua no v13.0, sem
alteração. Para `type: text` não há diferença documentada entre as duas: `preview_url` existe desde o beta da Cloud
API (changelog de 15/03/2022, mesma época do v13.0) e a página atual usa v25.0 no exemplo, com o mesmo formato. O
changelog da Cloud API não registra mudança no envio de `text` entre v13.0 e v22.0 (só uma mudança de webhook de
recebimento, em 20/10/2025). Diferença prática: só a versão no endereço.

## Limites conhecidos

- **A miniatura não é garantida.** Depende da página (tags Open Graph, imagem acessível) e do aplicativo do
  cliente; a Meta aceita a mensagem do mesmo jeito. Sem prévia, o cliente vê o link clicável. Não há como o
  painel saber se a miniatura apareceu: a confirmação é o teste real (aceite 11 da Issue).
- Uma documentação antiga da Meta dizia que a prévia só aparece depois de um modelo enviado, de conversa
  iniciada por link "clique para conversar" ou com o número salvo na agenda do cliente, e que endereço com IP em
  vez de nome não é reconhecido. A página atual não repete nada disso; não confirmado. O tipo aceita IPv4.
- Palavra com texto colado antes do esquema (`vejahttps://x.com`) conta como endereço; o aplicativo do cliente
  pode não reconhecê-la. Caso raro; a mensagem sai como texto do mesmo jeito.
- **A validação lê o texto renderizado do canal da conversa, não o do WhatsApp.** O módulo chama
  `error_for(body)` com `RichMessages.body_text(message)`, e o tipo não recebe a mensagem nem o `content` cru:
  validar sempre sobre a renderização do WhatsApp exige mudar `RichMessages.type_error` (arquivo comum, que vale
  também para o `link_button`). Não foi feito; está relatado à coordenação. Efeito hoje: no Telegram os 4096
  caracteres são medidos no HTML, que é maior que o texto do WhatsApp (corpo perto do limite pode ser recusado
  lá e aceito no WhatsApp); o corte em `"`, `<` e `>` resolve os casos de endereço conhecidos.
- O renderizador do WhatsApp troca `*` por `_` dentro do caminho do endereço
  (`https://exemplo.com.br/a*b*c` sai `.../a_b_c`): a prévia e o link vão para outro caminho. É do renderizador
  comum, igual no texto sem `rich_message`; não alterado aqui.
- Endereço sem página real com host de duas partes (`https://1.2`) é aceito: sai sem miniatura, com o corpo
  como está. A validação confere forma, não se a página existe.
- A pontuação final é tirada só para validar; o corpo vai à Meta como está. Endereço que termina em `)` de
  propósito (`.../Pagina_(desambiguacao)`) é validado sem o `)`, o que não muda o resultado da validação.
- Nenhum envio real à Meta: tudo com WebMock.
